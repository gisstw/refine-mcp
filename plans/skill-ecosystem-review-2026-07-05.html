§ 02 / 比喻

安檢機 vs 輸送帶上的行李

把「refine 自動審查」想成機場的安檢機：它對著輸送帶掃，看得到誰就能審誰。 問題是它只看「已經在系統裡登記過的行李」（也就是 git 知道的檔案）。 你剛放上輸送帶的新行李（新建的檔案）還沒入境登記，鏡頭掃過去 — 等於沒看到 — 直接放行。 修好之後，安檢機入口多鋪一塊壓力感應器，新放上來的就會亮橘色警告牌「這個還沒審」。

「入境登記」是什麼？Git 知道的檔案叫 tracked（已入境登記）。剛建好還沒告訴 git 的叫 untracked（剛放上輸送帶）。舊版安檢機只看第一種。
為什麼這是個漏洞？新建的 migration、新建的 .md 筆記、新建的腳本本來就是要拿來改東西的 — 恰恰是最需要被審查的，舊版反而看不到。
怎麼補的？舊版只用 git 看「有沒有改」。新版同時用 git 跟一份叫 ls-files --others 的指令（搬運工的主管發的命令）抓「有沒有新建」。
亮牌是什麼意思？新版的審查結果表會把剛建立的檔案標成 (untracked)，就像橘色警告牌：這個還沒正式入境，但你已經看到它了。

    § 08 / 風險 / 剩餘

    還有 2 件要處理

    這次沒處理到的兩件事在這裡公開列出來 — 不是「忘了」，是這次範圍刻意排除， 等你（使用者）拍板才動。

    01blast-radius 跨倉庫搜尋的限制

    這次只掃了 PMS 一個倉庫就能抓到問題，但實際上很多補丁會跨好幾個倉庫同時影響。 refine 預設只分析單一倉庫的「影響範圍」，所以跨倉庫影響的判斷可能不夠準。 目前靠人工「會注意」補上，但以後工程量變大會變成瓶頸。

    建議下一步：評估要不要加跨倉庫搜尋（或外部 MCP）。

    02chrome-devtools MCP 插件「還活著」的現象

    全域守則 §16.2 早已明文停用 chrome-devtools-mcp，改用 Playwright MCP。 但「外掛清單」指令 claude mcp list 仍顯示它 Connected — 狀態文字跟上層決策不一致。 不是功能問題，是「顯示跟事實對不上」會讓人誤判。

    建議下一步：請你決定 — (a) 真的把 chrome-devtools-mcp 從設定移除，或 (b) 保留但加上一行備註「已停用，僅 Playwright」。
